How a claim becomes a published verdict

A plain-language walkthrough of what happens between an article being picked up and a verdict appearing on a public page: where the material comes from, who decides what is worth checking, how one shared method of checking works, and what has to be true before anything goes public. Every step has more detail underneath it if you want it, and none of it is in the way.

Every claim goes through the same method. One question settles whose words each sentence is and whether we may check it at all; then a capped research loop does the rest — one part writes down what evidence would prove the claim and what would disprove it, another goes and finds it, and a third decides whether what was found is enough. Nobody's name or party enters the decision at any point.

Picking up new material on a schedule

Nobody presses a button. The system checks each source on its own timetable — and treats a source that goes quiet as a problem in its own right.

INGESTION §2.1 · STORE §2.3 · ADR-0006 · ADR-0012

Needs: the list of sources we follow Produces: a to-do item whenever a source is due to be checked Never: letting a silent source look like a healthy one
What happens, step by step
  1. We follow a fixed list of sources: government press releases, RNZ politics, a few broadcaster videos, one institution, and a small hand-picked set of miscaptioned items used for practice.
  2. Each source is checked on its own timetable — the news feeds every hour, the videos a few times a day (about 20 to 40 items a day in total).
  3. Nobody has to remember to run it. If a check is missed because the system was offline, it runs when the system comes back.
  4. A source that answers "success" but returns nothing at all is treated as a failure, not as a quiet day.
  5. A source that stops producing anything for longer than its usual rhythm raises a warning, even though nothing reported an error.
  6. The public coverage page is built from the same counts the operators see, so the two cannot disagree.
The most dangerous failure is silence. A broken source does not complain — it simply stops. So we watch for the absence of news, not only for error messages.
How the schedule worksin detail
  • The schedule lives in the database, not in a timer on a server. Each source has its own entry. When a check is due, a row is created for it, and a worker picks that row up.
  • Two workers can never take the same row. The database hands each row to one worker at a time, so the same check cannot run twice by accident.
  • A missed check is not lost. If a worker was offline when a check was due, the check runs when the worker comes back.
  • We keep the history. How long each run took, whether it worked, and how many times it retried are all recorded, and the alerts read from that history.
  • Each source is watched in five ways. Did the fetch work. Did the number of items look normal. How often did we need the harder reader. How long since the last new item. Did the job run at all.
  • Warnings follow a fixed ladder. Try again. Fall back to reading the page in a browser. Mark the source degraded. Tell a person. Then state the gap on the public coverage page.
  • The public coverage page and the operators' dashboard read the same numbers, so the two cannot tell different stories.
Doing it by hand — setting up one sourceby hand
  1. Decide the source and how often to check it. Write down its name, its feed address or how to reach it, the kind of publication it is, and the most requests a day we are willing to make.
  2. Create one row per due check, named after the time it belongs to, so running the same check twice does nothing.
  3. Let a worker take the row, note when it started and finished, and record whether it worked.
  4. Record, for every run: when it last ran, when it last worked, how many items it saw, how many were new, how often the harder reader was needed, whether the source is stale, and whether it is alerting.
  5. Set up an alert for when the heartbeats stop. A check that never runs sends nothing, so there is no error to alert on. The absence itself has to be the trigger.
Two different failures look alike and must not be treated as one. A feed that answers with no items, and a feed that is dead. Both make coverage shrink quietly, and they call for different responses.
What can go wrong, and how we catch iteverything
ING-R1If a feed breaks or freezes, we catch it two ways. A feed that stops producing new items is flagged as stale, and a feed that answers with no items raises its own alarm.
ING-R12If the health checks themselves stop working, a missing entry in the run history raises an alert. Monitoring that fails silently is worse than none at all.
STO-R18If a worker dies part-way through a job, the job stays marked as running. Past a set time that raises an alert, and the missed schedule is filled in when the worker restarts.
CRO-R19Alerts fire on silence, not only on errors. We test that case before launch, not after.
ING-R14If a site redesign pushes a whole source onto the harder reader, the number of fallbacks per source leaves its normal range and the source is flagged.

Collecting the article

We fetch each new item once, keep a copy of it, and write down where it came from and when we got it.

INGESTION §2.1–2.4, §3.1 · ADR-0006 · ADR-0007

Needs: the web address of a new item Produces: the item's text, saved with its address, the time we fetched it, and a unique code for its contents Never: paying to get past a paywall, or making our own recordings
What happens, step by step
  1. We read the source's own list of recent items. Each one comes with a title, a web address and a publication time.
  2. Anything we have already saved is skipped.
  3. We fetch the page and keep the text exactly as it arrived, so we never have to fetch it a second time.
  4. We record the address, the date and time we got it, and how we got it.
  5. We check we really got an article — not a "prove you are human" page, and not a paywall stub cut off mid-sentence.
  6. For videos we read the caption information the platform itself provides. If those captions were made automatically rather than checked by a person, we mark that, and treat the wording with extra caution.
  7. If an article sits behind a paywall, we use only the part that is publicly shown — and the page says so.
How the collection worksin detail
  • We read the feed first. Beehive (beehive.govt.nz/rss.xml, about 30 items) and the RNZ politics feed (about 16 items). Only once the feed reads cleanly do we fetch the item pages.
  • A feed we cannot read is an error, not an empty feed. If the file is malformed, or its shape is not what we expect, the run fails loudly.
  • We fetch each item once, here at the start. That saved copy is what we work from. When we come to check evidence we go back to the live source.
  • A paywall is a boundary, not a puzzle. We never pay to get past one and never work around one. A paywalled item can be a claim we check, but it is never the evidence for its own claim. We use only the part that is publicly shown.
  • For videos, the platform's own caption information decides how much we trust the wording. Captions marked as generated automatically are treated as unreviewed. A caption track with no such marker is treated as reviewed. If there is no track at all, the video is out of scope.
  • We stay inside a request budget per source. Captions are a handful of requests a day, read-only, and the budget is checked in tests.
Doing it by hand — collecting one itemby hand
  1. Fetch the feed. Read out each item's own id, its address, its title, its publication date and its summary. If that fails, fail the run. Do not treat it as a source with no new items.
  2. Skip any item whose id we already hold, or whose contents we already hold.
  3. Fetch the item page and keep the bytes exactly as they arrived.
  4. Check three things, in order. The request worked. The page is not a "prove you are human" screen. The page is not a paywall stub cut off mid-sentence.
  5. Write down the address, the time we fetched it, how we fetched it, and a code that stands for the contents.
  6. For videos, write down the kind of caption track, whether it was reviewed or automatic, and a code for the track. If the track changes later, we flag the claims that used it and find their place in the video again.
Retries are bounded. We try again, then fall back to reading the page in a browser, then mark the source degraded, then tell a person. Tests use a fake server returning 429, 500 and a bot-wall page, and check that we never fetch the same thing twice.

What can go wrong, and how we catch iteverything
ING-R1A dead or frozen feed is caught by the staleness check, and a feed answering with no items raises its own alarm.
ING-R3Automatic captions being mistaken for reviewed ones is tested against four cases: automatic only, reviewed only, both kinds present, and none at all.
ING-R4A broken "hear it" link is caught when we build the link from the stored timestamps, and again by loading the real link before release.
ING-R7Asking a platform for too much is caught by a request-budget test against a fake server.

Reading the words off the page

We take the text out of the page. When a page is built unusually we try harder — and we record what we had to do, because that is an early warning that the source has changed.

INGESTION §2.1, §3.1–3.2 · ADR-0006 · ADR-0007

Needs: the saved copy of the page Produces: the plain text, plus a note of which method worked Never: treating "we got nothing" as a success
What happens, step by step
  1. First we use a straightforward reader — the same idea as "reader view" in a browser. It takes the headline and the paragraphs.
  2. If that comes back empty, or the page is built unusually, we ask an AI model to pull out the text, and we record exactly why the first attempt failed.
  3. If that fails too, we try loading the page the way a browser would. If it still fails, we mark the source as degraded and say so publicly.
  4. We check the text for two specific kinds of damage: characters scrambled by bad encoding (which can mangle Māori macrons), and text that has been escaped twice so it shows up as odd symbols.
  5. Getting nothing back from a page that clearly has content counts as a failure. That is the worst kind of error, because everything looks fine.
  6. How often we need the harder fallback is itself a signal: when a site redesigns its pages, that number rises before anyone notices a problem.
How we get the text out — the three attemptsin detail
AttemptWhat we useWhen we reach for it
FirstA reader built for that kind of file. Feeds, ordinary article pages and caption files each get their own. Captions keep their timestamps.Always, every time.
SecondWe ask an AI model to pull the text out in a fixed shape we can check, and we record exactly why the first attempt failed.Only when the first attempt fails. We count how often this happens, per source.
ThirdA headless browser loads the page the way a real one would. If that fails too, we mark the source degraded and say so on the page.Only when the second attempt fails.

The failures are not thrown away. Every case we capture becomes a test, and a rising second-attempt rate is the first sign that a site has changed its pages.

Doing it by hand — articles and captionsby hand

An article page

  1. Take the headline from the page's main heading.
  2. Take the body from the article's paragraphs, in order. For a table, turn each row into one line with the values separated by a colon.
  3. If the page clearly has content and we got nothing out of it, stop and fail. This is the failure where extraction looks successful while dropping the text.
  4. Check for damage on the bytes we received, not on the page after our reader has tidied it. Look for two things: characters scrambled by mismatched encoding, which can damage Māori macrons, and text escaped twice, which shows up as stray symbols. Correct escaping is normal and must not be flagged.

A caption file

  1. Read each cue: its start time, its end time, the speaker if given, and the text. Both the long and the short timestamp forms appear in the wild.
  2. An empty file, or one with only a header, is marked degraded. It is never treated as a clean transcript.
  3. Build the "hear it" link from the stored start and end times, with a little padding either side. Nothing else may be used to build it.

Deciding what is ours to check

Two questions are asked of every sentence: whose words is it, and what is it. A sentence is checked only when both answers allow it, and a sentence we cannot check is written down with the reason — in the same record, every time.

TRIAGE §2.1–2.2, §2.5 · ADR-0008, ADR-0025

Needs: the article's sentences, and the kind of publication it is Produces: claims we may check, each with the class that let it through, plus one record of everything set aside Never: guessing who said something, or deciding anything from who the person is
Why this step exists. The project checks what people in public life say, not how a newsroom writes. So before anything is read as a claim, one decision settles whose words each sentence is. Whether it can be checked follows from that same decision.
Two questions, asked separately

The first question is whose words is this — because the project checks what people in public life say, never how a newsroom writes. The second is what is this — because even a person's own words can be an opinion, a rhetorical flourish or a joke, and none of those can be settled by evidence. The two overlap: a quoted actor can be stating an opinion, so one answer cannot carry both. A sentence is checked only when both answers allow it, and the record says which one stopped it.

What happens, step by step
  1. Where the page already tells us, we use that. A parliamentary transcript marks who was speaking; video captions mark when each line was said. Those are the record, not a guess.
  2. Otherwise the first question is asked of every sentence, in order: whose words is this? Narration and unattributable quotations stop here.
  3. The second question is then asked of the sentences that passed the first: is this a factual claim? A quotation can be an opinion or a joke, so this is a separate decision, not a consequence of the first.
  4. We note only the name the text itself gives. We do not fill in party, job title, or any kind of confidence score.
  5. A sentence the model did not answer becomes unresolved. A missing answer can never look like coverage.
  6. Every sentence ends up in one of two places: a claim, or the one record of what we set aside with the class that stopped it — from whichever question stopped it. There is no second record to reconcile.
  7. We count how many sentences survive this step for each source. If that count collapses it looks exactly like a healthy source producing nothing — so it raises a warning.
The rules that decide a class — and where they never lookin detail
  • The decision reads the sentence and the kind of publication, and nothing else. It is given no speaker name, no party and no history, so the same sentence cannot be judged differently by who said it.
  • The kind of publication selects the rule. A news report mislabelled as opinion would make the reporter's own assertions checkable, which is the dangerous direction. author-claim is available only for opinion and analysis.
  • A person merely mentioned is not its speaker. Narration is never attributed to someone the sentence only refers to.
  • A headline or standfirst is not a claim.
  • The two questions are independent, and that is the point. A quoted actor can be giving an opinion, so the second question is not implied by the first. A sentence that is someone's own words and an opinion is set aside as an opinion — the record names the reason that actually applies.
  • The second question runs only on what the first let through. Nothing is asked about a sentence the newsroom wrote.

In scope means elected politicians, parties and candidates, officials speaking for the government, and the institutions we follow. Journalists and newsrooms are sources of quotation, never claimants.

Doing it by hand — long documents, and the fail-closed ruleby hand
  1. Split the text into sentences with a fixed rule, not a model. For captions the cut has to keep each sentence attached to its place in the recording.
  2. Read the sentences in order, in batches of at most 20 sentences or 6000 characters. If a batch comes back in a shape we cannot read, retry it at half the size before failing the whole document.
  3. For a quotation, write down only the name the text itself gives. Do not fill in the party, the job title, or a confidence score. Nothing has yet worked out who that person is.
  4. Record how the decision was made and the kind of publication, because “the transcript tells us” and “a model read it” are different claims, and the public page says which one was used.
  5. If the decision is missing, or the method is missing, or the kind of publication is missing, the claim cannot be published. That is deliberate: no record means no page.
  6. Keep every set-aside sentence with its class and its provenance. Those records are how we measure what we might have missed.
Two rules do the real work here. Knowing who said something decides only whether a sentence may be checked. It never decides what the research finds. And the research never sees a person to reason about — only the text and the class.

What can go wrong, and how we catch iteverything
One class, one record. Every sentence of every document appears exactly once, either as a claim or in the drop log with the class that set it aside. The drop log is the single funnel the published “what we did not check” disclosure is built from.
Repetition is measured, not assumed away. Our models ignore the settings meant to make them repeatable, so the same sentence can be judged differently on two runs. Triage is measured and disclosed; the published verdict class is protected by the two-run rule (step 8).
TRI-R1 / R2Checking too much — opinions, satire, promises — is caught by fixtures that must not become claims. Missing real claims is caught by having people label a sample of the sentences we set aside at every full test run, and reporting the result as a number.
TRI-R5 / R6A wrong context note changes which evidence matters. Fixtures vary the context and assert that the relevant readings change. A note filled in from identity alone must come out empty.
TRI-R7The tidied-up version of a claim drifting from the original words is caught by keeping both, and by checking that the tidied version can be derived from the original and its window.
TRI-R11Automatic-caption wording being treated as reviewed is caught by requiring every caption claim to carry its tier and quality flags. A missing flag fails validation.
TRI-R12 / R13A sentence quietly disappearing on a shape error is caught by recording the failure and counting it. Reading the same document twice must produce the same claims with the same ids.
ING-R15 / R16 / R17The newsroom's own writing being checked as a claim, a quotation attributed to the wrong person, and a source quietly producing no eligible sentences are caught by fixtures over the real cases and by counting, per source, how many sentences survive.
Where this stands. The decision is built and runs on the live source. Working out the kind of publication from the text is not built; each source declares what it is. Until a source's records carry a complete decision, the site serves none of them. That is the gate working, not the site breaking.

Reading what the claim was arguing for

A second pass, run once per claim, reads the whole document and records the point the claim supports — plus the topic, the occasion, and any caveats the speaker attached.

TRIAGE §2.3 · ADR-0008, ADR-0026

Needs: the claim, and the whole document it came from Produces: what the claim was arguing for, its topic, its occasion, the speaker's caveats, and the words around it Never: filling a note in from who said it, their party, or what they said before

This is the second half of the same triage step. The class decision (step 3) says whether a sentence may be checked; this pass says what the claim is for, which is what the research is framed by. It reads the document, not the paragraph beside the sentence, because the argument a claim belongs to is not always next to it.

What we record, and where it comes from
NoteWhere it comes from, and what it changes
What it was arguing forRead from the whole document. The specific point the claim supports. This frames the research and produces the “as deployed” line on the page. Left blank when the document does not make the point.
The topicRead from the document. Seeds the questions we search for, and the topic pages on the site.
Where it was saidThe venue or occasion: “in the House”, “at a post-Cabinet press conference”. Null when the document does not say, and never the speaker's name.
The speaker's own caveatsAny qualification the speaker attached, such as “up from a low base”. These stop a fair statement from looking misleading.
The words around the claimKept word for word. This is the record a reader can check.
  • Every note is optional, and every one is stored as it was found. A claim with no notes at all still gets researched; the page simply shows no “as deployed” line.
  • Absent is data. If there is no document text to read, every note stays empty. It is never filled in from the claim alone.
  • None of these may be filled in from who said it, which party they belong to, or what they said before.
This pass changes which evidence counts as relevant, so a mistake here reaches the verdict. That is why it is a separate, recorded call with its own provenance rather than a guess made later.
How the pass worksin detail
  1. Take the claim and the whole document.
  2. Ask what the claim is doing in the document's argument: the point it supports, the topic, the occasion, and the speaker's own qualifications.
  3. Store every field as found. A field the document does not support is stored empty, never defaulted.
  4. Attach the result to the claim record, with the version of the instruction that produced it.

A claim whose sentence has no surrounding window still gets this pass; the document is the input. Only a document with no text at all leaves every note empty.

Doing it by hand — and what a missing note meansby hand
  1. Read the document once, whole.
  2. Write down the point the claim supports in the speaker's own argument — not the topic, and not a summary of the document.
  3. Write down the topic, the occasion, and the speaker's caveats, each only if the document says it.
  4. Attach the words around the claim verbatim, so the note can be audited against its source.
A missing note is a finding, not a gap to fill. If the document does not say what the claim was arguing for, the page shows nothing there. A generic paragraph would be worse than an empty line.

Not checking the same thing twice

An article fetched twice does not become two articles. A claim made again does not become a second verdict.

INGESTION §2.8, §3.1 · TRIAGE §2.4 · STORE §2.2

Needs: the item's address, the source's own item number, a code for its contents, and the claim's class Produces: either a genuinely new item, or a note that we have seen this one again Never: merging two similar-but-different claims into one
What happens, step by step
  1. Every saved item gets a code based on its contents, plus its web address and the source's own item number.
  2. If any of those match something we already hold, we do not save a second copy — we simply note that we saw it again.
  3. For claims, we compare the claim's wording against claims we already hold. A claim that appears again is recorded as said again, by whom, where and when, rather than starting a second check.
  4. But if two similar claims differ in who said them, in the period, or in what they were arguing for, they stay separate. Merging them would lose a real instance of the claim.
  5. Nothing we publish is ever withdrawn, so the collection only grows. Running any step again must produce the same result, never a duplicate.

Doing it by hand — and why running it twice is safeby hand
  1. Look for the item by its own id, then by its address, then by its contents code. If any of them match, stop. Update the time we last saw it, and the version of the process that read it.
  2. If nothing matches, save the item. Save a separate record for each part of a document, but only where the document really has parts: caption turns or transcript turns.
  3. Work out the claim-level matching inputs and pass them on. Merge nothing at this step.
  4. Pass on the document record, how we extracted it, and the claim decision. Never pass on a finished verdict. Never pass on a name for the research to reason about.
Running it again must change nothing. Any source can be read a second time, and doing so must produce the same set of claims: no duplicates, at most a new note that a claim was said again. We test this directly, because the failure would cost twice and leave near-identical claims in the record.

A claim cannot be taken back. The identity check cannot remove a claim that a later run would not make, so the record grows by everything any run has found. For a system whose verdicts are public and permanent, that is the right direction.

What can go wrong, and how we catch iteverything
ING-R5 / STO-R13Duplicates on a re-run are caught by fixtures: identical copies collapse on the item id or the contents code, and reading the same fixture twice leaves one document, not two.
ING-R6Two genuinely different claims being merged is caught by the same fixtures: identical copies collapse, and claims that are merely similar must stay apart.
STO-R4A search index going stale after a bulk load is caught by loading fixtures, applying the schema, and checking that near-match searches still find their neighbours.
STO-R11The matching key changing meaning between versions is caught by pinning a known pair of repeated claims. Any change that stops them matching shows up as something a reviewer reads.
CRO-R9A re-run creating duplicates is caught by a double-run test that asserts the same counts and the same ids.

Working out what would settle this claim

Before anything is searched, we write down what evidence would prove the claim and what would disprove it: the questions to answer, the searches to run, and one search aimed at showing the claim is wrong.

VERIFICATION §2.1, §2.5 · ADR-0020, ADR-0026

Needs: the claim, and what it was arguing for Produces: a written evidence plan — what would settle it, and the questions to answer Never: a plan that only looks for agreement, or a different standard for different people
What happens, step by step
  1. Read the claim and its context. What it asserts, what it supports, the topic, the occasion and the country it is about. Never who said it.
  2. Write down what would settle it. In plain words: what a decisive source would have to say, and where it would live — the agency that holds it. For a New Zealand claim that is normally stats.govt.nz, policedata.nz or the Ministry of Justice's NZCVS, and figure.nz, which curates official New Zealand series and links each one back to the agency that produced it. This is the provisional evidence plan the page shows.
  3. List the questions to answer. The sub-questions a researcher should work through — including the ones that would disprove the claim, not only the ones that would confirm it. A question that only seeks agreement is not verification.
  4. Leave the searching to the next step. The plan says what would settle the claim and what to ask; the researcher decides which searches to run and reads what comes back.
  5. On a later turn, chase the gaps. If the evidence was not enough, the critique comes back here, and the next plan must chase what the critique said was missing rather than repeating searches that found nothing.
  6. Write the plan down and show it. The page renders the provisional plan, so a reader can see what was sought next to what was found.
One shared method, not a list of checks. There is no library of checks to choose from. Every claim goes through the same method — plan, search, judge — so a claim is never sorted into a check that may or may not fit it. What differs between claims is the evidence the plan goes looking for, not the machinery.
One limit, stated openly. Nothing here can prove that one thing caused another. The plan can ask for evidence that two things changed at the same time; it cannot reach a causal finding. Where a claim is about cause, the page says so instead of letting a timing finding look like a causal one.
How the plan is madein detail
  1. Input: the claim, what it supports, the topic, the occasion and the jurisdiction. Claimant identity never enters.
  2. Output: an evidence plan — a plain-words statement of what would settle the claim, plus the questions a researcher should answer.
  3. Adversarial by construction. It is asked what would falsify as well as what would confirm, and the questions must include the ones that would disprove the claim.
  4. From turn two, the previous critique is an input: its gaps are what the next plan must chase. Queries that already found nothing are not repeated.
  5. The plan is provisional. It is not a promise of what ran; the loop record stores each turn's plan beside what was actually found and decided.
The site cannot work this out for itself. A page that guessed what evidence had been sought would be describing a step that nothing recorded, so the plan is stored and shown.
Doing it by hand — and what “settle it” meansby hand
  1. State what a decisive source would have to say — not where to look, but what it would have to establish.
  2. Break the claim into sub-questions that can each be answered by published evidence.
  3. Include the questions whose answers would show the claim is wrong or oversimplified. Keep them even when you expect to find nothing.
  4. Record the plan with the versions of the instruction that produced it.
No check can establish cause. About one claim in nine in our standard test set is about cause. The plan can seek timing evidence and report it as timing; it cannot show that one thing made another happen. Closing the gap means adding a way to seek a comparison — the trend before the policy started, and against a similar group it never touched — as another evidence source, not as a separate instrument. The page says so in the meantime.

Gathering the evidence

One part of the loop does all the searching. It is given the plan and a set of tools, and it decides for itself what to do next — search, read a page, pull the passages out, or stop — reading the result of each step before choosing the following one.

VERIFICATION §2.1, §2.4, §2.7 · ADR-0020, ADR-0026

Needs: the evidence plan, and the tools to act on it Produces: evidence — sources, the pages behind them, verbatim passages, and the links worth following Never: asserting what a page says beyond the words quoted from it
What happens, step by step
  1. It is given tools, not a list of searches. Search the web, read a page, pull the shortest passages out of pages, and finish the turn. Several searches can be run at once.
  2. It searches for the data, not the sentence. The plan names where the evidence would live, so the researcher targets those domains — including figure.nz, which curates official New Zealand series and points at the agency behind each one — rather than searching the claim's wording back at itself.
  3. It chooses what to do next from what came back. Read the results, follow a promising source, chase a question from the plan, or stop — rather than running a fixed list and handing over whatever it happens to get.
  4. At least one search must be aimed at refuting the claim, because a search that only looks for agreement is not verification.
  5. Passages are word for word. A passage that is not verbatim cannot be checked, so nothing is summarised or paraphrased, and nothing is asserted about a page beyond the words quoted from it.
  6. Every tool call is written down — which tool, what it was asked, and a short summary of what came back — so the retrieval path can be re-run and the record shows what was actually done.
  7. It stops at the per-turn budget, either by finishing the turn itself or when the step limit is reached, and a new turn starts if the evidence was not enough.
  8. A page that cannot be fetched is recorded as degraded rather than dropped silently.
Retrieval is the hard part. The reference benchmark shows that giving the reader the right evidence lifts accuracy far more than any change to the prose. So this is where the budget goes: search, fetch, follow, extract — bounded so a run cannot wander the open web.
What bounds the searching, and whyin detail
  • Per turn: a fixed number of searches, a fixed number of page fetches, and a fixed number of steps the agent may take before the turn ends.
  • Per claim: the whole loop is capped at five turns. When the cap is reached without the evidence being enough, the conclusion is “we could not verify this” and the reason the decision gave is published. A capped run is a finding about the record, named as one — never a silent weak verdict.
  • Each turn is recorded: its plan, the strategy the researcher chose, the searches it ran, every tool call, the evidence it found, and the decision it produced, so the record shows what was sought, what was done, what was found, and why the class followed.
  • Search engines that let us control the query are used, because the evidence record has to be reproducible.
Doing it by hand — a single turnby hand
  1. Work through the plan's questions. Choose the searches yourself, and do not add a country the claim is not about.
  2. Deduplicate results by address across every turn, so the same page is never counted twice.
  3. Fetch each new page and read the text. A page that will not load is recorded as degraded, not as empty.
  4. Ask for the shortest verbatim passage that bears on the claim from each relevant page, and nothing else. Never assert what a page says beyond its passage.
  5. Follow at most a fixed number of the links the pages themselves name, within the same fetch budget.
  6. Record the searches, the result addresses, the passages, and every tool call you made, on the evidence record.
Two limits stated here. We make no recordings of our own, and audio-only material is out of scope: a claim about what someone said is compared with the stored caption text, never with the audio. And some kinds of source can never be the evidence for a verdict — encyclopaedia pages, social posts, link aggregators, and the claimant's own material. They may be quoted; they may not carry a decisive finding.

Deciding if the evidence is enough

The same part of the loop that reads the evidence decides whether it settles the claim. That decision is the publication gate — and it is made twice, because our models move.

VERIFICATION §2.1–2.4 · VER-R2, VER-R16, VER-R17 · ADR-0020, ADR-0026

Needs: the claim, the plan, and all the evidence found across every turn Produces: the verdict, the reason, the remaining gaps, and one justification per finding — or nothing Never: a conclusion the evidence does not support
What happens, step by step
  1. Decide sufficiency. Is this evidence enough to prove or disprove the claim? The bar is published: one official record for the claim's own country that states the figure, or at least two independent sources from different places. A single non-official source is not enough, and commentary about a related fact is not enough.
  2. Name the answer and the reason. One of four verdicts, a confidence, a plain-language reason a reader can follow, the gaps that remain, and one justification per finding — each one something the cited evidence actually entails.
  3. If it is not enough and turns remain, the critique goes back to the plan step, and the next turn chases the gaps it named.
  4. If the cap is reached, the verdict is “we could not verify this” and the decision's reason is published. A capped run says that it stopped, not that there was no evidence.
  5. Then the two-run rule. An answer is published only when it comes out the same way twice. If the two runs disagree, nothing is published.
  6. Where a claim cannot be settled at all, the page says so plainly and invites corrections. That is a real outcome, not a failure.
The decision is the gate. The question “does this conclusion follow from the evidence?” is asked at the point the conclusion is chosen, so a claim whose evidence does not support its class cannot publish. That decision is made by an AI model, so it is measured against cases that must pass and cases that must fail, and against human judgement at every full test run.
The decision, and the two-run rulein detail

The decision

  • It reads everything gathered, across every turn, not just the last round.
  • Every justification must be entailed by the evidence it cites. A conclusion the evidence does not support is treated as a failed call, not as an implicit pass.
  • It states the loop's own bound: what the evidence cannot establish, in plain words on the page.
  • It applies the published source rules: some kinds of source can never be the record, a decisive verdict needs a source at sector-body level or better, and a claim needs one official record or two independent ones.

The two-run rule

  • Only an answer that comes out the same way twice is published. If the two runs disagree, we publish nothing and record the disagreement.
  • Why. Our models ignore the settings meant to make them repeatable: the same input moved between “we could not verify this” and “supported” on different runs. When we cannot pin the models down, we pin the decision instead.
  • The first run is the published one. Its reasoning comes from a run whose answer matched the other, and the rule is easy to state.
  • A failed call is not a disagreement. If a provider errors, that error is passed on. Counting outages as disagreement would swamp the real signal.
  • Two runs is a floor, not a target. A single run would agree with itself by definition.
What we do with the confidence numberby hand
  • Not reaching a verdict is a real outcome. The claim is published as an open question with its evidence attached, so anyone can add to it, and the page says we could not verify it.
  • The loop records a confidence number, but it is a model's own estimate of how settled the evidence is — not a probability that has been checked against real outcomes. Nothing has calibrated it yet, so the page does not present it as one. It comes back as a published number only once it has been measured against what actually happened. If it does, it will be small text, never a bar, a dial or a headline.
Watch the disagreement rate. How often the two runs disagree is our best sign of whether a decision is stable enough to publish at all. It belongs beside the failure rate of the decision, on the same page of numbers.

What can go wrong, and how we catch iteverything
VER-R2The decision passing things it should fail — a hallucinated or unsupported finding — is caught by cases that must pass and cases that must fail, by comparing the decision against human judgement in the full runs, and by alerting on a failure rate that is implausibly low.

Recording the verdict permanently

A verdict is added to, never edited. If it changes, we publish a new version showing exactly what changed and why.

STORE §2.1–2.7, §4 · ADR-0002, ADR-0005

Needs: the verdict, the evidence, and the versions of everything that produced it Produces: a permanent, versioned record that cannot be silently changed Never: editing or deleting a published verdict — by anyone, including us
What happens, step by step
  1. We save the claim, the evidence, our written reasoning, and the versions of everything that produced the verdict.
  2. Every piece of evidence carries two dates: when the data was published, and when we fetched it. Both are shown on the page.
  3. If a source later revises its figures, the record still shows exactly what the verdict relied on. A correction is a new version, never a change to the version already published.
  4. Nothing can be taken out of the record — not even evidence we rejected. Rejections are part of the public record.
  5. The rules are enforced by the database itself, so nobody can quietly edit history. That includes us.
  6. From 5 to 27 November 2026 — the pre-election freeze — the system refuses to change any published verdict at all.
The order things are written, and what each record holdsin detail
  1. The claim. Its identity is the sentence, the words around it, and the class hashed together. That makes the write safe to repeat: running the same work twice finds the claim instead of adding a second one.
  2. Each piece of evidence, as its own record: which source it came from, the name of the series, the date the data was published, the address, a snapshot of the source page, a contents code, and a version number. Fetching it again creates a new version. It never changes the version already published.
  3. The evidence record: which items were used, our written reasoning, and the loop's own record — each turn's plan, the evidence it found and the decision it produced, how many turns were used, and whether the cap bound. Once a verdict points at it, it is frozen.
  4. The verdict, version one: the answer, its state, the evidence record it rests on, the decision's confidence number, and the versions of everything that produced it.
  5. The change of state: from draft to published, with a reason. Every change is logged, including rejected evidence, which is logged and never taken out of the record.

The states a verdict can be in

DRAFT → PUBLISHED → CONTESTED → VALIDATING → MUTATED → AUDIT
                              ↘ back to PUBLISHED // evidence rejected, reason logged
         PUBLISHED → FROZEN  // 5–27 Nov 2026, enforced by the database

The states are part of the database, not a checklist someone follows. During the freeze window the database refuses any change to a published verdict. A contested verdict during the freeze is shown as contested and under review.

How “never edited” is enforcedby hand
  • Each part of the system has its own permissions. The part that writes verdicts can add rows and read them. It cannot change or delete one. The site can only read. The parts that produce the ground-truth labels have their own separate area, which the pipeline cannot open.
  • There is a second guard underneath. The database refuses an edit or a delete on every one of these tables, even for someone who had permission. Both guards are tested against a real database, including the attempt to edit a row.
  • A correction is a new row that points to the version before it. If a source revises its figures, the new version is added and the version already published still shows exactly what the verdict relied on.
  • Verdicts are numbered per claim, and a change carries a stored, field-by-field list of what changed. The public diff is generated from that list rather than worked out again later, so it cannot drift from what actually changed.
  • We store how the verdict was made, not what it cost. Token counts and the model are recorded for each call. Money is worked out later from one dated price list, so a price change re-prices the history without rewriting it.
Repeating work has the same shape. Reading a document again produces the same claims. Reading a source again produces no duplicates. Reprocessing a verdict adds a version instead of replacing one. The database hands each job to one worker at a time, and unique rules stop a double write if two ever try.

Publishing the page

A web page anyone can read — or nothing at all, if the claim is not ours to check.

SITE-MVP §2.2–2.7, §3 · STORE §3 · ADR-0002, ADR-0004

Needs: a published verdict and everything behind it Produces: a web page with the verdict, the evidence and the audit trail, plus machine-readable details for search engines Never: publishing a claim we cannot attribute, or hiding how a page was made
What happens, step by step
  1. Before anything is published, two conditions must hold: the claim came from a document we actually hold, and we have positively decided whose words it is, with the reason recorded.
  2. If either is missing, the page shows nothing. That is deliberate — no decision means not publishable.
  3. Every page leads with the claim and the verdict, in the same order every time.
  4. Below that is the audit trail: five dated sections in everyday words — what else was in the document and what we did not check; what the claim was read as and what evidence was sought; how the research works, what it found here and what it cannot show; what we compared it against; and the sufficiency decision with the versions of everything that ran.
  5. Nothing is hidden behind a click. If we do not hold a piece of information, the page says so rather than filling the gap.
  6. Each page carries machine-readable details that let search engines and fact-checking tools list it, and it is built to work with JavaScript turned off.
  7. The published accuracy figures are generated from the actual test run, never typed in by hand. If that file is missing, the site refuses to build rather than showing a blank table.
The gate before publication — two conditionsin detail

The site serves a claim only when both of these are true. It cannot work either one out for itself, so it does not guess.

  1. We hold the document it came from. That is what makes a check traceable to something a reader can open.
  2. We positively decided whose words it is, and recorded how we decided and what kind of publication it was. If any of those three is missing, the claim cannot be published.

Everything else is kept and not published: evaluation material, records written directly by our own scripts with no document behind them, the newsroom's own writing, quotations we could not attribute, and anything that carries no class decision. One rule gates both the page and the list, so a record cannot be listed but unreadable. We can still inspect all of it through a deliberate override, which is not the default.

This is deliberate. Because the step that decides whose words a sentence is does not yet run on every source, a lot of what we hold is unclassified — and the gate, which refuses anything incomplete, serves none of it. An empty site is the correct state here, not a fault.
The verdict page: fixed section order and the trailby hand

Every page, in the same order

  1. The claim, word for word, with who said it and the document it came from.
  2. The verdict mark. A band and a pin, never a dial or a smiley face.
  3. One sentence saying what the verdict means.
  4. The "as deployed" line, shown only when the words around the claim said what it was arguing for.
  5. A "hear it" or "watch it" link, shown only when we hold the clip's timestamps, with a note when the wording came from automatic captions.
  6. The evidence, strongest source first. Each item is linked, with the date the data was published and the date we fetched it. Source types are written in plain words, and the internal codes stay in the technical record.
  7. The audit trail: five dated sections, described below. All of them are open by default.
  8. Related claims, last.

Nothing is hidden behind a click, because an audit record a reader has to ask for is one most readers never see. Where we do not hold something, the section says so. It is never filled with a generic paragraph, and it never borrows another claim's explanation.

The five sections of the audit trail

#SectionWhere it comes from
1What else was in the document, and what we did not checkThe stored triage record: how many sentences we read, how many we checked, which we set aside and why, and which we held back.
2What the claim was read as, and what was soughtThe claim's class and the context it was read in, plus the provisional evidence plan the research followed.
3How the research works, what it found here, and what it cannot showThe stored research record — each turn's plan and decision — plus the limit the decision itself stated in plain words.

  • Each section prints its own audit line. The labels come from an approved list, and an unapproved label fails the build. The values print exactly as they were recorded, because a value ties the page to the run that produced it and a paraphrase can drift.
  • A step whose date we do not hold is left out. It is never guessed at.
  • The research is printed as it was recorded. Each turn's plan, the evidence found and the decision are read from the run, never reconstructed afterwards, so the page cannot describe a step that did not happen.
Being found by search engines, staying fresh, and the accuracy figuresby hand
  • Each page carries machine-readable details that let search engines and fact-checking tools list it: the address, who wrote it, the date it was published and any date it changed, the claim word for word, a rating, and the verdict in one sentence. Broken machine-readable data fails silently out in the world — the page is simply dropped with no error anywhere — so it is validated as the site is built, and the build fails loudly.
  • Everything that matters is in the server's first response, before any browser scripting runs: the verdict, the machine-readable data, and the clip link. That is what search engines, link previews and readers with scripting turned off receive.
  • A changed verdict updates the page within minutes. Our writer tells the site which pages to rebuild whenever a verdict changes. A change updates the content and the published date. The claim's address never changes, so links people have shared stay good.
  • The accuracy figures are generated, never typed in. A full test run writes a dated file recording the versions of everything used. The methodology page reads that file and prints the numbers. If the file is missing or unreadable, the site refuses to build rather than showing an empty table, and a build check asserts the printed numbers match the file.
  • Public pages use everyday words. A build check fails the page if it contains the internal vocabulary. The methodology page is the one page whose job is to explain the machinery, and it is allowed plain-English descriptions rather than jargon.

What an AI call is for, and where there is none

The model is used at the decisions listed below, and nowhere else. Sentence splitting, deduplication, the search and fetch budgets, the two-run rule, the append-only writes and the published page are all deterministic — the same inputs produce the same result, with the model's own variability measured and disclosed rather than hidden. When a model is used, the tier it runs on is chosen by what the output is for: evidence the decision judges runs on the research tier, and anything a reader sees runs on the stronger one.

The order the calls are made in

1 · Ingest
no AI

Fetch the item once, extract the text, record what the extraction had to do.

2 · Triage
triage-speakership→triage-checkability→triage-context

One class per sentence, batched over chunks of at most 20 sentences or 6000 characters (a truncated response is halved and retried). Then the context pass, once per checkable claim, over the whole document.

3 · Plan
claim-assessor

Writes the provisional evidence plan: what would prove or falsify the claim, where the evidence would live (the holding agency, and figure.nz for curated NZ series), and the questions to answer — including the ones that would disprove it. Verdict tier, because the plan frames everything the research looks for.

4 · Gather
researcher·search → read page → extract passages → finish·researcher-extract

A bounded tool loop: the researcher chooses its own searches and reads each result before choosing the next step, within the per-turn budget. Research tier, and the bulk of the calls per claim. It produces evidence the decision judges, not a published finding.

5 · Decide
evidence-critiquer

Sufficiency, class, reason, gaps and justifications. If it is not sufficient and turns remain, the critique returns to step 3. At the cap the class is “we could not verify this”, with the reason published. The deciding call runs a second time, and only an agreed class is published.

· Classify source
authority-classify

Source vetting: what kind of source a page is, on the A1–A6 authority map. An advocacy source is never a verdict basis.

6 · Publish
no AI

Write the append-only verdict version, the loop record, the transition log and the ClaimReview markup.

The instruction text behind each call

triage-checkability — triage-checkability@1 packages/pipeline/src/triage.ts

One call decides whose words each sentence is, and checkability follows from the class. Conservative by design: an unclear speaker is unresolved, never a guess. The output format is the schema the model is constrained with, so the prompt does not restate JSON.

You decide, for each sentence of a document, whose words it is — and therefore whether the sentence may be fact-checked at all. This is conservative by design: when the speaker is not clear from the text, the answer is "unresolved", never a guess.

You are given the document's genre and its sentences in order. Return exactly one class per sentence, in the order given, plus the speaker's name when the class is "quoted-actor" and null otherwise.

Classes:
- "quoted-actor": reported speech. The sentence is inside quotation marks, or its words are attributed to someone ("Macpherson says", "Hipkins told RNZ", "the report said"). A quotation may open in one sentence with the attribution verb in an adjacent one: read the neighbours and attribute to the speaker it is attributed to.
- "author-claim": the AUTHOR of an opinion or analysis piece asserting in their own voice. Only available when the genre is "opinion-analysis". Never for a news report: there the author is a journalist reporting, not claiming.
- "outlet-prose": the journalist or outlet narrating, summarising, setting the scene, or describing background. No speaker. A reporter's sentence that happens to contain a number is still outlet prose.
- "unresolved": a quotation with no resolvable speaker — an unattributed pull-quote, or one whose attribution is genuinely ambiguous.
- "opinion": an evaluation or value judgement, not a falsifiable assertion.
- "rhetoric": persuasive framing with no factual content.
- "procedure": a statement about proceedings rather than a factual claim.
- "satire": satire is set aside, never checked.
- "question": a question, not an assertion.
- "off-domain": outside the project's policy remit.
- "pledge-conditional": a commitment about what will happen; gradable only once its deadline passes.

Only "quoted-actor" and "author-claim" are checkable. Every other class is the reason the sentence is not checked.

Rules:
- A person merely mentioned in a sentence is NOT its speaker. Do not attribute narration to someone who is only referred to.
- Do not treat the document's headline or standfirst as a claim.
- The genre decides which rules apply: for "news-report", "author-claim" is not available.
triage-context — triage-context@1 packages/pipeline/src/triage.ts

Reads the whole document, not the paragraph beside the sentence, and answers what the claim is doing in the speaker's argument. Every field is optional and stored as found.

You are given a document and one claim made in it. Say what the claim is doing in the document's argument.

Answer four things:
- venue: where or on what occasion the words were said ("in the House", "at a post-Cabinet press conference", "on RNZ Morning Report"). Null when the document does not say. NEVER the speaker's name.
- topic: the policy topic the claim is about. Null when unclear.
- supports: the specific point the claim is used to support — why it matters to the argument being made. Read the WHOLE document to answer this, not just the sentence. Null when the document does not make the point.
- qualifiers: the speaker's own qualifications, verbatim where present.

All fields null (or empty) if absent. Never infer from who is speaking.
claim-assessor — claim-assessor@1 packages/pipeline/src/research.ts

Adversarial by construction: it is asked what would prove the claim and what would falsify it, so the falsification questions are required. It writes questions, not searches — the researcher chooses those. On a later turn it is given the previous critique, so the next plan chases the gaps rather than repeating searches that found nothing.

You are an adversarial claim assessor. Given a factual claim and the argument it was used to support, work out what evidence would PROVE it and what evidence would FALSIFY it.

Produce a research plan:
- evidencePlan: in plain words, what evidence would settle this claim — what a decisive source would have to say, and who would hold it.
- questions: the sub-questions a researcher should answer, in the claim's own jurisdiction and naming any entities the claim names. At least one must be a question whose answer would show the claim is FALSE or oversimplified: a plan that only seeks agreement is not verification.

You write questions, not searches — a researcher decides which searches to run and reads what comes back.

On a later turn you are given the previous critique: its gaps are what the next plan must chase. Do not ask again what already found nothing.
researcher — researcher@1 packages/pipeline/src/research.ts

The only role that touches the open web, and the only one that decides its own next step. It is given tools and the plan's questions, and reads each result before choosing what to do next. It pulls the shortest passage that speaks to the claim, verbatim — a passage that is not verbatim cannot be checked, so nothing is summarised or paraphrased. Every tool call it makes is recorded.

You are a researcher working through an evidence plan. You have tools; use them in whatever order the evidence requires, and read each result before choosing the next step.

Tools:
- "search": run a web search. You may call it several times in one step; the calls run in parallel. Include at least one search aimed at REFUTING the claim, not only at confirming it.
- "readPage": fetch the full text of a specific page you want to inspect.
- "extractEvidence": for a set of urls and a question, return the shortest VERBATIM passages that speak to the claim. Use this for the pages that matter; it returns checked quotations, not summaries.
- "finish": call when you judge the turn's searching done, with a one-sentence reason.

Chase the plan's questions, follow a promising source, or stop. Do not repeat a search that already found nothing.

Never assert what a page says beyond its passage.
researcher-extract — researcher-extract@1 packages/pipeline/src/research.ts

The extraction step behind the researcher's extractEvidence tool: given pages and one question, it returns the shortest verbatim passages that answer it, and nothing else.

You are extracting evidence. You are given a question and the text of pages.

For each page that bears on the question, return the url and the SHORTEST passage that answers it, verbatim from the page. If a page is not relevant, omit it. Do not summarise and do not paraphrase: a passage that is not verbatim cannot be checked.

Never assert what a page says beyond its passage.
evidence-critiquer — evidence-critiquer@1 · the publication gate packages/pipeline/src/research.ts

The sufficiency decision is the gate. Every justification must be entailed by the evidence it cites, and a conclusion the evidence does not support is treated as a failed call rather than an implicit pass.

You are an evidence critiquer. You are given a claim, the plan that was used to search for evidence, and ALL the evidence gathered across every turn. Decide whether that evidence is ENOUGH to prove or disprove the claim.

The bar: one official record for the claim's own jurisdiction that directly states the specific figure or statement, OR at least two independent sources from different domains. A single non-official source is NOT enough. Media commentary about related facts is NOT enough.

Answer:
- sufficient: whether the evidence settles the claim. If you answer false, say exactly what is missing in gaps.
- verdictClass: "supported" if the evidence establishes the claim; "refuted" if it establishes its negation; "conflicting_cherry_picking" if the evidence shows the claim is accurate but selective or incomplete; "not_enough_evidence" if it does not settle the claim.
- confidence: 0-1.
- reason: one or two plain sentences a reader can follow, saying why the class follows from the evidence.
- gaps: what specifically remains unverified, when not sufficient.
- justifications: one sentence per finding, each stating something the cited evidence entails. Never synthesize beyond the evidence; never attribute to a person a character judgement.

You must not conclude "supported" or "refuted" unless the evidence you cite entails it. A conclusion the evidence does not support is worse than not_enough_evidence.

What we cannot do (yet)

The things this system does not do. They are named on the public methodology page, and on the verdict page itself, rather than hidden behind a confident-sounding answer.

VERIFICATION §1, §5 · SITE-MVP §2.5

  • No part of the system can prove that one thing caused another. In the standard test set, about 11% of claims are about cause. The research can find that two things changed at the same time and report it as timing; it cannot show that one made the other happen. Every claim's page states this limit, and closing the gap means adding a way to seek a comparison — the trend before the policy started, and against a similar group it never touched — as another evidence source.
  • We make no recordings of our own, and audio-only material is out of scope. A claim about what someone said is compared against the record we hold, never against the audio itself.
  • Wording taken from automatic captions rests on unreviewed speech recognition. We mark those claims on the page, and a number quoted in a caption is checked against the official record, never against the caption.
  • There is no separate figures instrument. The pipeline does not compute alternative framings itself; a number claim is researched like any other, and the page says so. A deterministic series check would be added as an evidence source for the research, not as a separate instrument.
  • The loop records a confidence number, but nothing has calibrated it against real outcomes, so the page does not publish it as a probability. It becomes a published number only once it has been measured against what actually happened.
  • A claim said in different words is matched only by wording. Near-duplicates are caught by comparing the claim's wording; the embedding that would catch a rephrasing with no words in common is not wired, so a rephrasing may be missed.
  • There is no instrument for “false context”. A claim that a photo, clip or document comes from a different event is researched like any other claim, and we do not claim a dedicated capability to detect it.
  • Our AI models cannot be fully pinned down. They give slightly different answers to identical input, so we measure that variation and disclose it rather than hide it — which is why the published class is decided twice before it is published.
  • Research is capped. A claim that needs more searching than the cap allows is published as “we could not verify this”, with the reason the decision gave and a record that the cap bound. That is a finding about the record, not a claim that the evidence does not exist.
  • Māori-language coverage is limited. Macron round-tripping is a tested byte-exact invariant, but that is text integrity, not language coverage — and the gap is named on /methodology.
  • Contest-and-correction features, reader submissions, and chain-of-argument views are not built yet. The database can record those steps; the current build exercises the journey from draft to published, and that gap is itself treated as a risk.

  • The four test layers: L1 deterministic, every push, where nearly all work happens · L2 ~20 pinned claims producing a snapshot verdict and evidence path, every PR, a readable diff required · L3 the reference benchmark plus a stratified NZ set with real spend, weekly and pre-release, gated per stratum · L4 rendered-page and markup validation every push, plus a deploy smoke.
  • The blind rule is structural, not conventional. Labels live in a separate database with no grants to the pipeline identity; packages/pipeline must never import @cw/harness; label credentials never enter pipeline env. Tests enforce role denial, import direction, and env separation, and they are never weakened.
  • No hand-edited numbers. The published accuracy table is rendered from a run file carrying its whole provenance tuple. A re-run is auditable; a hand-edit is not.
  • One concern per commit, conventional commits with a package scope and an em-dash summary, naming the risk id or ADR satisfied where one applies. Work lands on main; CI is the gate.
