How a claim becomes a published verdict

A plain-language walkthrough of what happens between an article being picked up and a verdict appearing on a public page: where the material comes from, who decides what is worth checking, how each kind of check works, and what has to be true before anything goes public. Every step has more detail underneath it if you want it, and none of it is in the way.

A claim is not sorted into one of a fixed set of checks. It gets a plan — the list of checks that claim needs — and the checks themselves are a list we keep and add to. That change is the newest thing in this document, and it is the reason a claim can now be checked two ways at once.

Picking up new material on a schedule

Nobody presses a button. The system checks each source on its own timetable — and treats a source that goes quiet as a problem in its own right.

INGESTION §2.1 · STORE §2.3 · ADR-0006 · ADR-0012

Needs: the list of sources we follow Produces: a to-do item whenever a source is due to be checked Never: letting a silent source look like a healthy one
What happens, step by step
  1. We follow a fixed list of sources: government press releases, RNZ politics, a few broadcaster videos, one institution, and a small hand-picked set of miscaptioned items used for practice.
  2. Each source is checked on its own timetable — the news feeds every hour, the videos a few times a day (about 20 to 40 items a day in total).
  3. Nobody has to remember to run it. If a check is missed because the system was offline, it runs when the system comes back.
  4. A source that answers "success" but returns nothing at all is treated as a failure, not as a quiet day.
  5. A source that stops producing anything for longer than its usual rhythm raises a warning, even though nothing reported an error.
  6. The public coverage page is built from the same counts the operators see, so the two cannot disagree.
The most dangerous failure is silence. A broken source does not complain — it simply stops. So we watch for the absence of news, not only for error messages.
How the schedule worksin detail
  • The schedule lives in the database, not in a timer on a server. Each source has its own entry. When a check is due, a row is created for it, and a worker picks that row up.
  • Two workers can never take the same row. The database hands each row to one worker at a time, so the same check cannot run twice by accident.
  • A missed check is not lost. If a worker was offline when a check was due, the check runs when the worker comes back.
  • We keep the history. How long each run took, whether it worked, and how many times it retried are all recorded, and the alerts read from that history.
  • Each source is watched in five ways. Did the fetch work. Did the number of items look normal. How often did we need the harder reader. How long since the last new item. Did the job run at all.
  • Warnings follow a fixed ladder. Try again. Fall back to reading the page in a browser. Mark the source degraded. Tell a person. Then state the gap on the public coverage page.
  • The public coverage page and the operators' dashboard read the same numbers, so the two cannot tell different stories.
Doing it by hand — setting up one sourceby hand
  1. Decide the source and how often to check it. Write down its name, its feed address or how to reach it, the kind of publication it is, and the most requests a day we are willing to make.
  2. Create one row per due check, named after the time it belongs to, so running the same check twice does nothing.
  3. Let a worker take the row, note when it started and finished, and record whether it worked.
  4. Record, for every run: when it last ran, when it last worked, how many items it saw, how many were new, how often the harder reader was needed, whether the source is stale, and whether it is alerting.
  5. Set up an alert for when the heartbeats stop. A check that never runs sends nothing, so there is no error to alert on. The absence itself has to be the trigger.
Two different failures look alike and must not be treated as one. A feed that answers with no items, and a feed that is dead. Both make coverage shrink quietly, and they call for different responses.
What can go wrong, and how we catch iteverything
ING-R1If a feed breaks or freezes, we catch it two ways. A feed that stops producing new items is flagged as stale, and a feed that answers with no items raises its own alarm.
ING-R12If the health checks themselves stop working, a missing entry in the run history raises an alert. Monitoring that fails silently is worse than none at all.
STO-R18If a worker dies part-way through a job, the job stays marked as running. Past a set time that raises an alert, and the missed schedule is filled in when the worker restarts.
CRO-R19Alerts fire on silence, not only on errors. We test that case before launch, not after.
ING-R14If a site redesign pushes a whole source onto the harder reader, the number of fallbacks per source leaves its normal range and the source is flagged.

Collecting the article

We fetch each new item once, keep a copy of it, and write down where it came from and when we got it.

INGESTION §2.1–2.4, §3.1 · ADR-0006 · ADR-0007

Needs: the web address of a new item Produces: the item's text, saved with its address, the time we fetched it, and a unique code for its contents Never: paying to get past a paywall, or making our own recordings
What happens, step by step
  1. We read the source's own list of recent items. Each one comes with a title, a web address and a publication time.
  2. Anything we have already saved is skipped.
  3. We fetch the page and keep the text exactly as it arrived, so we never have to fetch it a second time.
  4. We record the address, the date and time we got it, and how we got it.
  5. We check we really got an article — not a "prove you are human" page, and not a paywall stub cut off mid-sentence.
  6. For videos we read the caption information the platform itself provides. If those captions were made automatically rather than checked by a person, we mark that, and treat the wording with extra caution.
  7. If an article sits behind a paywall, we use only the part that is publicly shown — and the page says so.
How the collection worksin detail
  • We read the feed first. Beehive (beehive.govt.nz/rss.xml, about 30 items) and the RNZ politics feed (about 16 items). Only once the feed reads cleanly do we fetch the item pages.
  • A feed we cannot read is an error, not an empty feed. If the file is malformed, or its shape is not what we expect, the run fails loudly.
  • We fetch each item once, here at the start. That saved copy is what we work from. When we come to check evidence we go back to the live source.
  • A paywall is a boundary, not a puzzle. We never pay to get past one and never work around one. A paywalled item can be a claim we check, but it is never the evidence for its own claim. We use only the part that is publicly shown.
  • For videos, the platform's own caption information decides how much we trust the wording. Captions marked as generated automatically are treated as unreviewed. A caption track with no such marker is treated as reviewed. If there is no track at all, the video is out of scope.
  • We stay inside a request budget per source. Captions are a handful of requests a day, read-only, and the budget is checked in tests.
Doing it by hand — collecting one itemby hand
  1. Fetch the feed. Read out each item's own id, its address, its title, its publication date and its summary. If that fails, fail the run. Do not treat it as a source with no new items.
  2. Skip any item whose id we already hold, or whose contents we already hold.
  3. Fetch the item page and keep the bytes exactly as they arrived.
  4. Check three things, in order. The request worked. The page is not a "prove you are human" screen. The page is not a paywall stub cut off mid-sentence.
  5. Write down the address, the time we fetched it, how we fetched it, and a code that stands for the contents.
  6. For videos, write down the kind of caption track, whether it was reviewed or automatic, and a code for the track. If the track changes later, we flag the claims that used it and find their place in the video again.
Retries are bounded. We try again, then fall back to reading the page in a browser, then mark the source degraded, then tell a person. Tests use a fake server returning 429, 500 and a bot-wall page, and check that we never fetch the same thing twice.

What can go wrong, and how we catch iteverything
ING-R1A dead or frozen feed is caught by the staleness check, and a feed answering with no items raises its own alarm.
ING-R3Automatic captions being mistaken for reviewed ones is tested against four cases: automatic only, reviewed only, both kinds present, and none at all.
ING-R4A broken "hear it" link is caught when we build the link from the stored timestamps, and again by loading the real link before release.
ING-R7Asking a platform for too much is caught by a request-budget test against a fake server.
ING-R9A paywalled item being treated as complete is caught by a fixture that must mark the claim as checked against its own wording and nothing else.
ING-R11A caption track being edited after we stored it is caught by comparing the track's contents code. When it changes, the claims using it are flagged.

Reading the words off the page

We take the text out of the page. When a page is built unusually we try harder — and we record what we had to do, because that is an early warning that the source has changed.

INGESTION §2.1, §3.1–3.2 · ADR-0006 · ADR-0007

Needs: the saved copy of the page Produces: the plain text, plus a note of which method worked Never: treating "we got nothing" as a success
What happens, step by step
  1. First we use a straightforward reader — the same idea as "reader view" in a browser. It takes the headline and the paragraphs.
  2. If that comes back empty, or the page is built unusually, we ask an AI model to pull out the text, and we record exactly why the first attempt failed.
  3. If that fails too, we try loading the page the way a browser would. If it still fails, we mark the source as degraded and say so publicly.
  4. We check the text for two specific kinds of damage: characters scrambled by bad encoding (which can mangle Māori macrons), and text that has been escaped twice so it shows up as odd symbols.
  5. Getting nothing back from a page that clearly has content counts as a failure. That is the worst kind of error, because everything looks fine.
  6. How often we need the harder fallback is itself a signal: when a site redesigns its pages, that number rises before anyone notices a problem.
How we get the text out — the three attemptsin detail
AttemptWhat we useWhen we reach for it
FirstA reader built for that kind of file. Feeds, ordinary article pages and caption files each get their own. Captions keep their timestamps.Always, every time.
SecondWe ask an AI model to pull the text out in a fixed shape we can check, and we record exactly why the first attempt failed.Only when the first attempt fails. We count how often this happens, per source.
ThirdA headless browser loads the page the way a real one would. If that fails too, we mark the source degraded and say so on the page.Only when the second attempt fails.

The failures are not thrown away. Every case we capture becomes a test, and a rising second-attempt rate is the first sign that a site has changed its pages.

Doing it by hand — articles and captionsby hand

An article page

  1. Take the headline from the page's main heading.
  2. Take the body from the article's paragraphs, in order. For a table, turn each row into one line with the values separated by a colon.
  3. If the page clearly has content and we got nothing out of it, stop and fail. This is the mistake that once made extraction look successful while dropping the text.
  4. Check for damage on the bytes we received, not on the page after our reader has tidied it. Look for two things: characters scrambled by mismatched encoding, which can damage Māori macrons, and text escaped twice, which shows up as stray symbols. Correct escaping is normal and must not be flagged.

A caption file

  1. Read each cue: its start time, its end time, the speaker if given, and the text. Both the long and the short timestamp forms appear in the wild.
  2. An empty file, or one with only a header, is marked degraded. It is never treated as a clean transcript.
  3. Build the "hear it" link from the stored start and end times, with a little padding either side. Nothing else may be used to build it.

Working out who said it

Some sentences are a person's own words. Others are the newsroom writing. Only someone's own words can be checked.

ADR-0019 · INGESTION §2.9 · TRIAGE §1

Needs: the article's sentences, and the kind of publication it is Produces: for each sentence, whose words it is and whether we may check it Never: guessing who said something
Why this step exists. In an early run we published a verdict about a sentence a journalist had written themselves. That is not our job — we check what people in public life say, not how a newsroom writes. So before anything is read for checking, we work out whose words each sentence is.
Whose words is it?
Whose wordsExampleCan we check it?
A person we can name“Crime is up 30%,” the Minister said.Yes
An opinion writer, in their own voice“This policy will fail,” in a column.Yes, if it is a factual claim about politics.
The newsroom's own writing“The Department also works on international policy…”No — we note it and leave it alone.
A quotation with nobody we can identify“We were never told,” a spokesperson said.No — we never guess.
What happens, step by step
  1. Where the page already tells us, we use that. An official parliamentary transcript marks who was speaking and video captions mark when each line was said — that is the record, not a guess.
  2. Otherwise we read the sentences in order and decide whose words each one is.
  3. We note only the name the text itself gives. We do not fill in party, job title or any kind of confidence score.
  4. We record how we decided, because “the transcript tells us” and “a model read it” are different claims, and the public page says which one was used.
  5. If we cannot tell, we do not guess. The sentence is recorded and never checked.
  6. We count how many sentences survive this step for each source. If that count collapses it looks exactly like a healthy source producing nothing — so it raises a warning.

The kind of publication decides the rule

In scope means elected politicians, parties and candidates, officials speaking for the government, and the institutions we follow. Journalists and newsrooms are sources of quotation, never claimants.

Doing it by hand — and the two rules that never guessby hand
  1. Use the page's own structure wherever it has one. A parliamentary transcript marks who was speaking. Video captions mark when each line was said. A press release is written by the body that published it. None of these needs a judgement call, so none of them gets one, and we record that we used the record rather than a reader.
  2. Where there is no structure, read the sentences in order, in batches of at most 20 sentences or 6000 characters. If a batch comes back in a shape we cannot read, retry it at half the size before failing the whole document.
  3. For a quotation, write down only the name the text itself gives. Do not fill in the party, the job title, or a confidence score. Nothing has yet worked out who that person is.
  4. Record how each sentence was decided. "The transcript tells us" and "a model read it" are different claims, and the public page has to say which one it was.
  5. If the decision is missing, or the method is missing, or the kind of publication is missing, the claim cannot be published. That is deliberate: no record means no page.
Two rules do the real work here. Knowing who said something decides only whether a sentence may be checked. It never decides what the check finds. And the check itself never sees a person to reason about: it gets a yes-or-no flag and a name the text gave.

What can go wrong, and where this stands todayeverything
ING-R15The newsroom's own writing being checked as a claim is caught by a fixture in which both the narration and a quotation assert something. Only the quotation may become a claim.
ING-R16A quotation attributed to the wrong person is caught by fixtures covering the real cases: attribution inside one sentence, across two sentences, an unattributed pull-quote, an opinion writer's own claim, transcript markup, and a forwarded press-release line. Where this stands. The reader that makes this decision is built, and it runs on the live source. Working out the kind of publication from the text is not built; each source declares what it is. Until a source's records carry a complete decision, the site serves none of them, and we read them separately. That is the gate working, not the site breaking.

Not checking the same thing twice

An article fetched twice does not become two articles. A claim made again does not become a second verdict.

INGESTION §2.8, §3.1 · TRIAGE §2.4 · CROSS-CUTTING §6 · STORE §2.2

Needs: the item's address, the source's own item number, and a code for its contents Produces: either a genuinely new item, or a note that we have seen this one again Never: merging two similar-but-different claims into one
What happens, step by step
  1. Every saved item gets a code based on its contents, plus its web address and the source's own item number.
  2. If any of those match something we already hold, we do not save a second copy — we simply note that we saw it again.
  3. For claims, we look for a near-match on what the claim is actually about — using a comparison of the claim's wording, not a hand-built key. A claim that appears again is recorded as said again, by whom, where and when, rather than starting a second check.
  4. But if two similar claims differ in who said them, in the period, or in what they were arguing for, they stay separate. Merging them would lose a real instance of the claim.
  5. Nothing we publish is ever withdrawn, so the collection only grows. Running any step again must produce the same result, never a duplicate.

A near match is a question, not a merge. If two claims are similar but differ in who said them, in the period, or in what they were arguing for, they stay separate. Merging them would swallow a real instance.
Doing it by hand — and why running it twice is safeby hand
  1. Look for the item by its own id, then by its address, then by its contents code. If any of them match, stop. Update the time we last saw it, and the version of the process that read it.
  2. If nothing matches, save the item. Save a separate record for each part of a document, but only where the document really has parts: caption turns or transcript turns.
  3. Work out the claim-level matching inputs and pass them on. Merge nothing at this step.
  4. Pass on the document record, how we extracted it, whose words we think each sentence is, and the matching inputs. Never pass on a finished verdict. Never pass on a name for the check to reason about.
Running it again must change nothing. Any source can be read a second time, and doing so must produce the same set of claims: no duplicates, at most a new note that a claim was said again. We test this directly, because the failure would cost twice and leave near-identical claims in the record.

A claim cannot be taken back. The identity check cannot remove a claim that a later run would not make, so the record grows by everything any run has found. For a system whose verdicts are public and permanent, that is the right direction.

What can go wrong, and how we catch iteverything
ING-R5 / STO-R13Duplicates on a re-run are caught by fixtures: identical copies collapse on the item id or the contents code, and reading the same fixture twice leaves one document, not two.
ING-R6Two genuinely different claims being merged is caught by the same fixtures: identical copies collapse, and claims that are merely similar must stay apart.
STO-R4A search index going stale after a bulk load is caught by loading fixtures, applying the migrations, and checking that near-match searches still find their neighbours.
STO-R11The matching key changing meaning between versions is caught by pinning a known pair of repeated claims. Any change that stops them matching shows up as something a reviewer reads.
CRO-R9A re-run creating duplicates is caught by a double-run test that asserts the same counts and the same ids.

Deciding what is worth checking

For every sentence we ask: could this be checked against evidence? If not, we write down why we set it aside.

TRIAGE §2 · ADR-0004, ADR-0008, ADR-0019

Needs: the sentences that survived the “whose words” step Produces: claims worth checking, each with its kind and its context — plus a record of everything set aside Never: a verdict, or a confidence score
What happens, step by step
  1. Checkable means a specific factual statement: a number, a quotation, or a claim resting on a document.
  2. Not checkable means opinion, rhetoric, questions, procedural talk, or satire. Satire is deliberately set aside, never “checked”.
  3. A promise about the future is not checkable as a fact. It can only be checked later, as “did they do what they said”.
  4. We also work out what kind of claim it is. That does not pick the check — the next step builds the plan — but it decides which checks the plan is required to consider.
  5. We note what the claim was arguing for — taken only from the words around it, never from who said it.
  6. Every sentence we set aside is kept, with its reason. Those records are how we measure what we might have missed.
  7. Long articles are read in batches, so a very long piece cannot quietly be half-read.
“Is this checkable?” is a judgement, and it is made by an AI model. We measure how often it gets that right and publish the number, rather than pretending the judgement is exact.
What this step does, one thing at a timein detail
  1. Split the sentences. We cut the text into sentences with a fixed rule, not a model. For captions the cut has to keep each sentence attached to its place in the recording, because automatic captions often have no punctuation to cut on.
  2. Ask whether each sentence is checkable. The answer is one of three. Checkable. Not checkable, meaning opinion, rhetoric, procedure or satire. Or a promise, which cannot be checked yet. Satire is set aside and never checked. A promise can only be checked later, as "did they do what they said".
  3. Work out what kind of claim it is. This does not pick the check — the plan does, in the next step. It decides which checks the plan is required to consider: a number claim must have the figures check decided on, a quotation must have the recording check decided on.
  4. Note the claim's context, from the words around it. Those notes decide which alternative readings matter later, so a mistake here reaches the verdict. They are listed below.
  5. Write down every sentence we set aside, with the reason. Those records are how we measure what we might have missed.

Long documents are read in batches

  • At most 20 sentences or 6000 characters at a time, whichever comes first.
  • If a batch comes back in a shape we cannot read, we retry it at half the size before failing the document.
  • The count of sentences read covers the whole document. A document that was only partly read can never be recorded as fully read, and a batch that still fails stops the run instead of quietly shrinking what we claim to have looked at.
  • If two batches disagree about which model answered them, the run fails rather than recording the first batch's model for all of them.
  • A response cut off by a length limit is recorded as cut off, not as "the model did not answer".

Where the design and the code differ — then what can go wrongeverything
Where the design and the code differ. The design showed two separate steps: one to decide the kind of claim, and one to build a matching key for it. In the code, deciding the kind happens inside the same call as the checkability question — and the key-building step has since been deleted rather than left unwired. Nothing ever read the key, and the only two things anything took from it were the claim's period and its number, which are now read properly in the figures check itself. A test pins which steps this part of the process calls, and which one it does not, so switching typing on is a decision rather than an accident.
The other gap is repetition. Our models ignore the settings meant to make them repeatable, so the same sentence can be judged differently on two runs. That is why the final answer is decided twice before it is published.
TRI-R1 / R2Checking too much — opinions, satire, promises — is caught by fixtures that must not become claims. Missing real claims is caught by having people label a sample of the sentences we set aside at every full test run, and reporting the result as a number.
TRI-R3Typing a claim wrongly is the costliest mistake here. A number claim typed as something else never makes the figures check required, so the strongest verdict becomes unreachable without anything looking wrong. Fixtures assert the type, and the plan's required checks follow from it.
TRI-R5 / R6A wrong context note changes which alternative readings matter. Fixtures vary the context and assert that the relevant readings change. A note filled in from identity alone must come out empty.
TRI-R7The tidied-up version of a claim drifting from the original words is caught by keeping both, and by checking that the tidied version can be derived from the original and its window.
TRI-R11Automatic-caption wording being treated as reviewed is caught by requiring every caption claim to carry its tier and quality flags. A missing flag fails validation.
TRI-R12 / R13A sentence quietly disappearing on a shape error is caught by recording the failure and counting it. Reading the same document twice must produce the same claims with the same ids.

Working out what this claim needs

A claim gets a plan: the list of checks it needs. Some claims need two — a quoted number needs the quotation checked and the figure checked. Nobody's name or party is involved.

VERIFICATION §2.1 · plan.ts · ADR-0023 (replaces ADR-0005 §2.1 mode routing)

Needs: the claim, what it says, and the list of checks we know how to run Produces: the plan — every check this claim will get, and any we considered and did not run, with the reason Never: a different standard for different people, or a check quietly left out
What happens, step by step
  1. Look at what the claim actually says. Does it state a number? Does it quote someone? Does it rest on a document? That is all the planner is allowed to look at — never who said it, and never their party.
  2. Some things force a check. A claim that states a number must have the figures check decided on. A claim that quotes someone must have the recording check decided on. A claim that rests on a document must have that document check decided on. We may still decide not to run one — but the decision and the reason are written down.
  3. Ask what worked before. We keep a list of the checks we know how to run, each with a note of what it can and cannot establish. For this subject, we look at which checks past plans used, and put the most-used first. That is a suggestion.
  4. Add anything else that is needed. The planner may add a check that is not on the list at all — including one we have never run before. The list advises; it never decides.
  5. Write the plan down and show it. Every step records which check, which version of it, why it is there, and whether it ran or was declined. The page shows the plan.
  6. Never leave out a check the claim needed. If a required check is not in the plan, the plan is refused rather than published.

  • The same claim gets the same treatment whoever says it. The planner cannot see the speaker, and it never looks at the claim's wording for tone or framing — only for what kind of thing the claim is.
  • We say which checks ran and which we declined. A check that was considered and not run is printed with the reason. Staying silent about it would read as though we had done it.
  • There is no fixed set of five. The checks are a list we keep and add to. Early on it holds the five below; when a claim needs a kind of check we have not built, the plan can name it anyway, and the gap is visible rather than hidden behind a weaker check.
One limit, stated openly. Nothing here can prove that one thing caused another. Our checks can show that two things changed at the same time; not that one caused the other. Where a claim is about cause, the page says so instead of letting a timing finding look like a causal one.
Doing it by hand — and why the decision is keptby hand
  1. Work out the claim's subject, from the claim's own words. That subject, not the claim text, is what the suggestions are keyed on — so two claims about the same subject get the same suggestions whatever they say about it.
  2. Note what the claim does: states a number, quotes someone, rests on a document, was deployed in support of a proposal. Those are the features that force a check to be considered.
  3. Look up which checks past plans for this subject used, most-used first. Keep that as a suggestion.
  4. Build the plan: the required checks first, then the suggestions, then anything the planner wants to add. Mark each one as to run or declined, and give a reason for every decline.
  5. Check the plan against the rule: every required check must appear. Refuse the plan if one is missing, rather than publishing it.
  6. Store the plan with the evidence record, and record which version of the check list suggested it, so the run can be reproduced.
The site cannot work this out for itself. Whether a number claim could actually be checked against official figures depends on a lookup the reader cannot see, so the plan is stored and shown on the page. A page that guessed would be publishing a claim about which checks ran when nothing recorded one.
No check can establish cause. About one claim in nine in our standard test set is about cause. The checks we have test numbers, documents, quotations and attachments. None of them can show that one thing made another happen. A claim about cause is planned onto open-web research, where any timing evidence is reported as timing and the causal part is left unassessed. Closing that gap means adding a check — comparing the trend before the policy started, and against a similar group it never touched — not re-routing the claim. The page says so in the meantime.

Checking it

The checks we can run. Each one says what it can establish, and what it cannot — and a claim can be checked more than one way.

VERIFICATION §2.2–2.8 · ADR-0005, ADR-0007, ADR-0018, ADR-0020, ADR-0023

Needs: the claim, what it was arguing for, and the official sources or recordings it can be matched against Produces: the evidence, the figures we computed, our written reasoning, and the outcome of the second-reasoning check Never: an opinion about the person who said it

What applies to every check
  • Every claim gets a real search before we give up. A check that finds nothing does not simply stop — it keeps going, with more research, before we will say we could not settle it. “We could not find enough evidence” is meant to be expensive to reach, so that it means we looked hard.
  • A decisive answer needs proper sourcing. Either an official record, or at least two independent sources. One blog post is never enough.
  • We search for evidence the claim is wrong, not only for evidence that supports it. At least one search is always aimed at refuting the claim.
  • We never take a search engine's top result as the answer. In an early run we “verified” a claim about policing using a politician's Wikipedia page — a page that did not mention the claim. So some kinds of sources can never be the evidence for a verdict.
  • For numbers we compute the alternatives ourselves. Not just the figure the speaker used, but the same figure a fixed set of other ways — different start dates, per person rather than in total, different comparison groups — and we show all of them. That set of ways is fixed in advance and identical for every speaker, so nobody is held to a standard invented after the fact.
  • A number can be true and still mislead. We have a separate verdict for that: “accurate but incomplete”. A true but selective number is never called false.
7a · Official figures (stat-grid)in detail

What this check cannot establish: that one thing caused another. It can show that two things changed at the same time. It cannot show that one caused the other.

  1. Read the claim's period and its number. Two things are taken from the claim's own words: the period it is about, and the size of the change it asserts. Both are read as structured values, not as free text — the period as a start year and an end year, the number as a kind and a value. If the claim states a change but the number cannot be read, we stop here and report that we could not read it, rather than grading the claim on direction alone.
  2. Look for what we already hold. If the same figures are already in our evidence store, use those, with their recorded dates. If they are not, fetch the series from the official source named for that subject. A fetch resumes from what we already hold; it does not start again.
  3. Save the series with its own date. Every series is stored with the date the data was published, not the date we fetched it, plus a snapshot of the source page. The numbers in the claim's own press release are never the evidence. We go to the official series and work the figure out ourselves.
  4. Work out the alternative readings. The ways of counting are fixed in advance and identical for every speaker. We work out four things: the same period the claim used; the same period starting two years later; the same change per person rather than in total; and every year-on-year change in the series.
  5. Ask the model which readings are relevant, and nothing else. The model marks which of the readings we computed bear on how the claim was used. It never invents a reading and never does arithmetic. A missing population figure leaves the per-person reading blank rather than producing a fake rate.
  6. Compare the claim's number with the readings, using fixed limits:
    What we findWhat we publish
    No official series covers this claimnot enough evidence
    No number in the claim, and every year-on-year change in the window risessupported
    No number in the claim, and the direction is not consistentnot enough evidence
    We cannot compute a reading for the period the claim usednot enough evidence
    The number runs the same way and is within 10 percentage points of the readingsupported
    The number runs the other way, or is more than three times the readingrefuted
    The right direction, but the number is inflatedaccurate but incomplete

    Both limits are fixed numbers written into the code. A true but selective number is never called false. "Does not match the evidence" is for a number that matches no reading at all. "Accurate but incomplete" is for a number that is real but leaves out the reading that changes the impression.

  7. Show the "as deployed" line only when the context note exists. If the surrounding words do not say what the claim was arguing for, the page shows nothing there. It is never filled in from who said it.
Why the model is kept away from the arithmetic. The fair objection to statistical fact-checking is that the checker invents its standard after seeing the claim. Here the readings are fixed and versioned, the arithmetic is plain logic with exhaustive tests, and the model only points at readings that already exist. The arithmetic is checked against a hand-computed example, reading by reading.

The page leads with the figures, then a table of the alternative readings, and shows the ways of counting that were used. That includes the readings that disagree with the claim.

7b · The source it cites (citation-check)in detail

What this check cannot establish: anything about a document we cannot get. If the cited source is paywalled or unreachable, the page says the claim was checked against its own wording and nothing else.

  1. Fetch the cited document from the server. If it is paywalled, the claim is checked against its own wording only. We never work around a paywall.
  2. Compare the claim with the document, within limits. Does the document say what the claim says it says: the numbers, the period, the group, the direction. This is a careful reading task rather than open-ended research, so it runs on a stronger model and is checked against a fixture set.
  3. Write down how closely the check binds. If the citation is doing real work in the claim's argument, the check binds tightly. If the citation is decorative, it does not. For a paywalled citation no comparison happened at all, so this is left blank rather than filled in.
  4. Keep the citation in its place. The cited document is what we check the claim against. It is never the evidence for the claim. If an institution's own statistic is a number claim, it is checked against the official figures instead. A campaigning group's numbers never decide a verdict.
  5. State the result as claim against source. When they disagree, the disagreement is the finding. It is never written up as a remark about the person who said it.
7c · The recording (quote-fidelity)in detail

What this check cannot establish: a quotation that appears in no published record. If we cannot find the words, the page says so. It does not say the person was misreported.

  1. Start from what we hold. The claim carries its place in the recording, the kind of caption track, and the timestamps of the line.
  2. Compare the claim's wording with the stored caption text, not with the audio. We make no recordings of our own. Audio-only material is out of scope, and the methodology page says so.
  3. Expect the known caption errors. Automatic captions confuse similar-sounding words, drop punctuation and join sentences wrongly, and format numbers inconsistently. Māori words are often misread. A caption error is not a misquotation, and the check must not report one.
  4. Carry the caution onto the page. A number quoted in a caption is checked against the official figures, never against the caption. A claim whose exact wording matters is published as "verification limited to the quoted claim". A claim from an automatic track carries a note that the wording rests on unreviewed speech recognition.
  5. Build the link from the stored timestamps only. If a claim cannot be placed in the recording, it is published as an open question rather than as a verdict with a link that goes nowhere.
7d · The context it carries (provenance · practice set only)in detail

What this check cannot establish: why someone attached a clip or an image to the wrong event. The record can show where something comes from. It cannot show what anyone intended.

  • It only runs on the practice set. The code refuses to run it on anything else. There is no schedule, no health check and no alerting for it, and we do not claim it can find false context on live material.
  • How it works. We take what the post claims about where the material comes from, then look for the original: when it was first published, by whom, and where. We compare the claimed context with the recorded one.
  • What it can find. "False context" is a finding in its own right: the content is genuine, but the when, the where or the who is wrong. The page shows the true context beside the claimed one.
  • What it produces for now. Numbers per group of claims, and a demonstration. The methodology page says exactly that.
7e · Open-web research — the capped catch-allin detail

What this check cannot establish: a fact nobody has published, or causation. It reports what is published and where the searching stopped. Finding no evidence is reported as finding no evidence, never as proof that the claim is false.

This is the least reliable check, so it is capped, labelled, and the most obviously open to challenge. The rules below are what stop "we could not verify this" from meaning "we did the minimum and gave up".

  1. Every claim gets a real search before we give up. If the evidence we hold cannot settle a claim, it gets a proper research pass before any verdict. A check that finds nothing usable keeps going with a search rather than stopping short. And a citation check with no cited document never runs at all.
  2. Break the claim into questions, not search terms. Up to six separate questions, each with one or two searches. A claim sentence makes a poor search; the things it is about make good ones. We do not add a country to the search unless the claim is about that country. If the questions cannot be worked out, the claim itself becomes the question so that the search still runs.
  3. Search what we hold first, then the web. We search our own stored evidence before going out. We use search engines that let us control the query, because the evidence record has to be reproducible. Every query and every result address is written onto the evidence record.
  4. Decide what counts as a source, in two passes. A fixed list removes some sources straight away: known campaigning groups, foreign government sites, and anything not served over https. Everything that survives is classified in one batch by an AI model as official, academic, mainstream media, sector body, or unknown, with a reason recorded. Some sources can never be the evidence for a verdict, whatever they would score: encyclopaedia pages, social posts, link aggregators, and the claimant's own biography.
  5. Require a real source for a decisive answer. To publish "supported" or "does not match the evidence", we need a source at sector-body level or better. Below that, the honest answer is that we could not verify it — or, where the only live question is whether someone said it, a finding about who said it.
  6. Look for the other side, and look twice. For a factual claim we need either one official record for the right country that states the figure, or at least two independent sources from different places. One non-official source is not enough, and commentary about a related number is not enough either. At least one of the searches must be aimed at showing that the claim is wrong. A search that only looks for agreement is not verification.
  7. Assess what we have and chase what is missing. The researcher reads the results, says what is still missing, and issues searches aimed at those gaps rather than repeating what we already ran. It reports whether the evidence is enough, its current reading, and a confidence number.
  8. Stop at the cap, and say that we did. The search has a fixed budget of twelve searches. If we hit it, the evidence record shows that we stopped at the cap rather than running out of evidence. Finding nothing at all leaves the confidence at zero. A confident answer from a model that saw no evidence is the exact thing this prevents.

Two last checks before we publish

Two independent checks stand between a worked-out answer and a public verdict. Either one can stop it.

VERIFICATION §2.7, §2.7a · VER-R2, VER-R16 · ADR-0002, ADR-0004

Needs: our written reasoning and the evidence behind it Produces: either a published verdict, or nothing at all Never: publishing when the two checks disagree
What happens, step by step
  1. First check. Does our written reasoning actually follow from the evidence we cite? Every sentence of our explanation has to be supported by the source beside it.
  2. If it does not, nothing is published — the case goes to a person to review instead.
  3. Second check. We work out the same answer twice, independently, and only publish an answer that comes out the same way both times.
  4. If the two runs disagree, we publish nothing and record the disagreement.
  5. If we cannot reach a verdict at all, the page says so plainly and invites corrections. That is a real outcome, not a failure.
  6. We do not publish a confidence percentage. Nothing here measures one, and an invented number would be worse than none.
Both checks are made by AI models, and we say so. The reasoning check catches the worst mistakes; it is not a guarantee of truth. And the two-run rule exists because our models give slightly different answers to identical input — so rather than pretending to be certain, we measure how often they disagree and publish that number.
How the two checks workin detail

First check: does our reasoning follow from the evidence?

Every sentence of our written reasoning has to be supported by the source beside it before anything is published. This is not a spot check afterwards. It runs before publication.

  • One pass over the whole evidence record, not one per sentence. If the response does not give an answer for every sentence, the check has failed. It is never read as a pass. A record with a single sentence keeps the single-sentence form.
  • It also enforces two writing rules: nothing asserted without a source, and any arithmetic stated out loud.
  • It can fail for four reasons: something asserted with no source, arithmetic left unstated, a source treated as proof because it was cited, or something invented that is not in the evidence.
  • A failure stops publication and sends the case to a person.
  • We say plainly what this is. The check is made by an AI model. It is measured against a set of cases that must pass and a set that must fail, and against human judgement in the full test runs. It catches the worst mistakes. It is not proof that the reasoning is correct.

Second check: do two independent runs agree?

The decision is made at least twice, and only an answer that comes out the same way both times is published. If the two runs disagree, we publish nothing and record the disagreement.

  • Why we do it this way. The obvious alternative does not work. Our models ignore the settings meant to make them repeatable, so the same input moved between "we could not verify this" and "supported" on different runs, while the first check passed every time. When we cannot pin the models down, we pin the decision instead.
  • The first run is the published one. Its reasoning comes from a run whose answer matched the other runs, and the rule is easy to state.
  • A failed call is not a disagreement. If a provider errors, that error is passed on. Counting outages as disagreement would swamp the real signal.
  • Two runs is a floor, not a target. A single run would agree with itself by definition.
  • We deliberately do not do this during the earlier sifting step, which runs once per sentence per document and would multiply the main cost. We measure the variation there instead, and disclose it.
Why we do not publish a confidence figureby hand
  • Not reaching a verdict is a real outcome. It is not a failure. The claim is published as an open question with its evidence attached, so anyone can add to it, and the page says we could not verify it.
  • Nothing in the system measures confidence, so we publish none. An early version wrote a placeholder figure of 0.7 into every verdict, which is how every page came to read "Confidence: 70%". That was removed. It comes back only when something actually produces a confidence value and that value has been checked against real outcomes. When it does, it will be small text, never a bar, a dial or a headline.
Watch the disagreement rate. How often the two runs disagree is our best sign of whether a decision is stable enough to publish at all. It belongs next to the failure rate of the first check, on the same page of numbers.
What can go wrong, and how we catch iteverything
VER-R2The reasoning check passing things it should fail is caught by cases that must pass and cases that must fail, by comparing the check against human judgement in the full runs, and by alerting on a failure rate that is implausibly low.
VER-R16An answer moving between runs is caught by tests in both directions: agreement publishes the first run, disagreement publishes nothing and records both answers, and an error is passed on rather than counted as a disagreement.
VER-R12Confidence being badly calibrated is caught by edge cases around the threshold, and by a calibration table in every full run.
SIT-R6A confidence figure appearing on a public page is caught twice: in the page's data model, and in the rendered page itself.
TRI-R10A provider quietly changing its model is caught by comparing pinned examples on every change, so the difference shows up as something a reviewer reads.

Recording the verdict permanently

A verdict is added to, never edited. If it changes, we publish a new version showing exactly what changed and why.

STORE §2.1–2.7, §4 · ADR-0002, ADR-0005

Needs: the verdict, the evidence, and the versions of everything that produced it Produces: a permanent, versioned record that cannot be silently changed Never: editing or deleting a published verdict — by anyone, including us
What happens, step by step
  1. We save the claim, the evidence, our written reasoning, and the versions of everything used to produce the verdict.
  2. Every piece of evidence carries two dates: when the data was published, and when we fetched it. Both are shown on the page.
  3. If a source later revises its figures, the record still shows exactly what the verdict relied on. A correction is a new version, never a change to the old one.
  4. Nothing can be deleted — not even evidence we rejected. Rejections are part of the public record.
  5. The rules are enforced by the database itself, so nobody can quietly edit history. That includes us.
  6. From 5 to 27 November 2026 — the pre-election freeze — the system refuses to change any published verdict at all.
The order things are written, and what each record holdsin detail
  1. The claim. Its identity is the sentence, the words around it, and the kind of claim hashed together. That makes the write safe to repeat: running the same work twice finds the claim instead of adding a second one.
  2. Each piece of evidence, as its own record: which official source it came from, the name of the series, the date the data was published, the address, a snapshot of the source page, a contents code, and a version number. Fetching it again creates a new version. It never changes the old one.
  3. The evidence record for this check: which items were used, the figures we worked out, our written reasoning, and the outcome of the reasoning check. Once a verdict points at it, it is frozen.
  4. The verdict, version one: the answer, its state, the evidence record it rests on, and the versions of everything that produced it. No confidence figure, because nothing measured one.
  5. The change of state: from draft to published, with a reason. Every change is logged, including rejected evidence, which is logged and never deleted.

The states a verdict can be in

DRAFT → PUBLISHED → CONTESTED → VALIDATING → MUTATED → AUDIT
                              ↘ back to PUBLISHED // evidence rejected, reason logged
         PUBLISHED → FROZEN  // 5–27 Nov 2026, enforced by the database

The states are part of the database, not a checklist someone follows. During the freeze window the database refuses any change to a published verdict. A contested verdict during the freeze is shown as contested and under review.

How “never edited” is enforcedby hand
  • Each part of the system has its own permissions. The part that writes verdicts can add rows and read them. It cannot change or delete one. The site can only read. The parts that produce the ground-truth labels have their own separate area, which the pipeline cannot open.
  • There is a second guard underneath. The database refuses an edit or a delete on every one of these tables, even for someone who had permission. Both guards are tested against a real database, including the attempt to edit a row.
  • A correction is a new row that points at the one it replaces. If a source revises its figures, the new version is added and the old one still shows exactly what the verdict relied on.
  • Verdicts are numbered per claim, and a change carries a stored, field-by-field list of what changed. The public diff is generated from that list rather than worked out again later, so it cannot drift from what actually changed.
  • We store how the verdict was made, not what it cost. Token counts and the model are recorded for each call. Money is worked out later from one dated price list, so a price change re-prices the history without rewriting it.
Repeating work has the same shape. Reading a document again produces the same claims. Reading a source again produces no duplicates. Reprocessing a verdict adds a version instead of replacing one. The database hands each job to one worker at a time, and unique rules stop a double write if two ever try.

What can go wrong, and how we catch iteverything
STO-R1 / CRO-R12History being edited is caught by tests that attempt an edit and a delete on every protected table, using the real permissions. A migration that changes old rows fails review.
STO-R2A missing version or diff is caught by writing one version, simulating new evidence, writing a second, and checking that the number went up, that a diff exists, and that the old version points at the new one.
STO-R3The date the data was published being confused with the date we fetched it is caught by requiring a published date on every series record, and by asserting the two are different.
STO-R9A change of state that should be refused but is not is caught by testing every legal and illegal change, including a change during the freeze. We rehearse the freeze in October.
STO-R10A verdict stored without a full record of how it was made is refused by the write path.
STO-R15Context notes being filled in by default instead of left absent is caught by refusing defaulted values, and by fixtures that must stay empty when the words around the claim say nothing.

CRO-R8 / R13Cost numbers being wrong, and the shared record shapes drifting apart, are caught by requiring every call to record its model and its token counts, and by asserting the two schema versions match before a test run scores anything.

Publishing the page

A web page anyone can read — or nothing at all, if the claim is not ours to check.

SITE-MVP §2.2–2.7, §3 · STORE §3 · ADR-0002, ADR-0004

Needs: a published verdict and everything behind it Produces: a web page with the verdict, the evidence and the audit trail, plus machine-readable details for search engines Never: publishing a claim we cannot attribute, or hiding how a page was made
What happens, step by step
  1. Before anything is published, two conditions must hold: the claim came from a document we actually hold, and we have positively decided whose words it is, with the reason recorded.
  2. If either is missing, the page shows nothing. That is deliberate — no decision means not publishable.
  3. Every page leads with the claim and the verdict, in the same order every time.
  4. Below that is the audit trail: five dated sections in everyday words — what else was in the document and what we did not check; what the claim was read as and which check it got; how that check works, what it did here and what it cannot show; what we compared it against; and the second look at our own reasoning.
  5. Nothing is hidden behind a click. If we do not hold a piece of information, the page says so rather than filling the gap.
  6. Each page carries machine-readable details that let search engines and fact-checking tools list it, and it is built to work with JavaScript turned off.
  7. The published accuracy figures are generated from the actual test run, never typed in by hand. If that file is missing, the site refuses to build rather than showing a blank table.
The gate before publication — two conditionsin detail

The site serves a claim only when both of these are true. It cannot work either one out for itself, so it does not guess.

  1. We hold the document it came from. That is what makes a check traceable to something a reader can open.
  2. We positively decided whose words it is, and recorded how we decided and what kind of publication it was. If any of those three is missing, the claim cannot be published.

Everything else is kept and not published: evaluation material, records written directly by our own scripts with no document behind them, the newsroom's own writing, quotations we could not attribute, and anything classified before this rule existed. One rule gates both the page and the list, so a record cannot be listed but unreadable. We can still inspect all of it through a deliberate override, which is not the default.

This is deliberate, and dated. Because the step that decides whose words a sentence is does not yet run on every source, a lot of what we hold is unclassified — and the gate, which refuses anything incomplete, serves none of it. An empty site is the correct state here, not a fault.
The verdict page: fixed section order and the trailby hand

Every page, in the same order

  1. The claim, word for word, with who said it and the document it came from.
  2. The verdict mark. A band and a pin, never a dial or a smiley face.
  3. One sentence saying what the verdict means.
  4. The "as deployed" line, shown only when the words around the claim said what it was arguing for.
  5. A "hear it" or "watch it" link, shown only when we hold the clip's timestamps, with a note when the wording came from automatic captions.
  6. The evidence, strongest source first. Each item is linked, with the date the data was published and the date we fetched it. Source types are written in plain words, and the internal codes stay in the technical record.
  7. The audit trail: five dated sections, described below. All of them are open by default.
  8. Related claims, last.

Nothing is hidden behind a click, because an audit record a reader has to ask for is one most readers never see. Where we do not hold something, the section says so. It is never filled with a generic paragraph, and it never borrows a different check's explanation.

The five sections of the audit trail

#SectionWhere it comes from
1What else was in the document, and what we did not checkThe stored record of the sifting step: how many sentences we read, how many we checked, which we set aside and why, and which we held back.
2What the claim was read as, and which check that producedThe kind of claim, and the recorded check it got.
3How this kind of check works, what it did here, and what it cannot showThe recorded check, matched to an explanation written once for that kind of check and applied to this claim.
4What we compared it againstThe evidence, with the date the data was published and the date we fetched it.
5The second look at our own reasoningThe outcome of the first check, and the versions of everything that ran.
  • Each section prints its own audit line. The labels come from an approved list, and an unapproved label fails the build. The values print exactly as they were recorded, because a value ties the page to the run that produced it and a paraphrase can drift.
  • A step whose date we do not hold is left out. It is never guessed at.
  • A number claim with no recorded check never falls back to its kind. A number claim reaches the figures only when the official source is listed, and the general search otherwise, so guessing would publish a check that never ran.
Being found by search engines, staying fresh, and the accuracy figuresby hand
  • Each page carries machine-readable details that let search engines and fact-checking tools list it: the address, who wrote it, the date it was published and any date it changed, the claim word for word, a rating, and the verdict in one sentence. Broken machine-readable data fails silently out in the world — the page is simply dropped with no error anywhere — so it is validated as the site is built, and the build fails loudly.
  • Everything that matters is in the server's first response, before any browser scripting runs: the verdict, the machine-readable data, and the clip link. That is what search engines, link previews and readers with scripting turned off receive.
  • A changed verdict updates the page within minutes. Our writer tells the site which pages to rebuild whenever a verdict changes. A change updates the content and the published date. The claim's address never changes, so links people have shared stay good.
  • The accuracy figures are generated, never typed in. A full test run writes a dated file recording the versions of everything used. The methodology page reads that file and prints the numbers. If the file is missing or unreadable, the site refuses to build rather than showing an empty table, and a build check asserts the printed numbers match the file.
  • Public pages use everyday words. A build check fails the page if it contains the internal vocabulary. The methodology page is the one page whose job is to explain the machinery, and it is allowed plain-English descriptions rather than jargon.

SIT-R1 / R2Broken machine-readable data, or accuracy figures drifting from the test-run file, are caught by extracting and validating the data from every rendered page, by failing the build when the file is missing or unreadable, and by asserting the printed table matches the file.

The four verdicts

What a reader sees at the top of a page, and what produces it.

ADR-0004 · VERIFICATION §2.2 · SITE-MVP §2.2

The verdictWhat it meansHow it happens
Backed by the evidenceThe evidence supports the claim as it was made.The official figures agree; or the document the claim cites says what the claim says; or the wording matches the recording.
Accurate but incompleteThe number is real, but the way it is used gives a misleading impression.Other readings of the same figures point the other way — for instance, the same change is much smaller once population is taken into account.

What we cannot do (yet)

The things this system does not do. They are named on the public methodology page, and on the verdict page itself, rather than hidden behind a confident-sounding answer.

VERIFICATION §2.1, §5 · SITE-MVP §2.5

  • No check can prove that one thing caused another. In the standard test set, about 11% of claims are about cause. Every check states this limit on the page, and the open-web one names it explicitly. Closing the gap means adding a check — comparing trends before and after, or against a group the policy did not touch.
  • We make no recordings of our own, and audio-only material is out of scope. The wording check compares a claim against the record we hold, never against the audio itself.
  • Wording taken from automatic captions rests on unreviewed speech recognition. We mark those claims on the page, and a number quoted in a caption is checked against the official figures, never against the caption.
  • “False context” checking is demonstration-only: it runs on a small hand-picked set of known miscaptioned items, and we do not claim it works on live material yet.
  • We do not measure confidence, so we publish none. It returns only once something actually produces a confidence value and that value has been checked against real outcomes.
  • A claim said in different words is only found by wording similarity. A hand-built key for matching the same figure across phrasings was designed and then deleted: nothing read it, and it could not identify a quotation or a cited document at all. Matching today is a wording-similarity search, which catches near-duplicates but not a rephrasing with no words in common.
  • The list of checks we can run is short, and it is not a fixed set. Five checks are built. A claim that needs a kind of check we have not built can have it named in its plan, but until it exists the claim is researched rather than properly checked — and the plan says so on the page.
  • Our AI models cannot be fully pinned down. They give slightly different answers to identical input, so we measure that variation and disclose it rather than hide it — which is also why every verdict is decided twice before it is published.
  • Māori-language coverage is limited. Macron round-tripping is a tested byte-exact invariant, but that is text integrity, not language coverage — and the gap is named on `/methodology`.
  • Contest-and-correction features, reader submissions, and chain-of-argument views are not built yet. The database can already record those steps; the current build only exercises the journey from draft to published, and that gap is itself treated as a risk.
